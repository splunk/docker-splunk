```markdown
# Supply Chain Verification

This document provides instructions for verifying the integrity and provenance
of Splunk Operator release artifacts.

## Image Verification

Each Splunk Operator release includes operator container images signed with
Cosign using a key-pair signing scheme.

> **Note:** Cosign signing is planned for a future release. The commands below
> will work once signing is enabled.

### Prerequisites

- [cosign](https://docs.sigstore.dev/cosign/installation/) installed locally
- The Splunk Operator public key: `cosign.pub` (committed at the root of this repository)

### Verify a Release Image

Replace `{VERSION}` with the release version (e.g., `3.1.0`):

```sh
# Download the public key
curl -fsSL https://raw.githubusercontent.com/splunk/splunk-operator/main/cosign.pub -o cosign.pub

# Verify the standard operator image
cosign verify --key cosign.pub splunk/splunk-operator:{VERSION}

# Verify the distroless operator image
cosign verify --key cosign.pub splunk/splunk-operator:{VERSION}-distroless
```

To verify a specific digest (pinned verification):

```sh
cosign verify --key cosign.pub splunk/splunk-operator:{VERSION}@sha256:<DIGEST>
```

The image digests for each release are listed in the `signing-summary.md` asset
on the [GitLab release page](https://cd.splunkdev.com/sok/splunk-operator/-/releases).

## SBOM Download & Inspection

Splunk Operator releases include CycloneDX SBOMs for the standard and
distroless operator images, generated by [Syft](https://github.com/anchore/syft).

### Download SBOMs

SBOMs are available as assets on the GitLab release page. Replace `{VERSION}`
with the release version:

```sh
# Standard operator image SBOM
curl -fsSL \
  https://cd.splunkdev.com/sok/splunk-operator/-/releases/v{VERSION}/downloads/sbom/sbom-operator-v{VERSION}.cyclonedx.json \
  -o sbom-standard.json

# Distroless operator image SBOM
curl -fsSL \
  https://cd.splunkdev.com/sok/splunk-operator/-/releases/v{VERSION}/downloads/sbom/sbom-operator-v{VERSION}-distroless.cyclonedx.json \
  -o sbom-distroless.json
```

### Vulnerability Scanning

Use the SBOMs with a vulnerability scanner to audit known CVEs in the release:

```sh
# Scan with grype (Anchore)
grype sbom:sbom-standard.json

# Scan with trivy (Aqua Security)
trivy sbom sbom-standard.json
```

### Inspect SBOM Contents

```sh
# Count components
jq '.components | length' sbom-standard.json

# List all packages
jq -r '.components[] | "\(.name) \(.version)"' sbom-standard.json

# Check SBOM metadata
jq '.metadata' sbom-standard.json
```

## BOM Overview

In addition to SBOMs (which enumerate software packages inside images), each
release includes a custom Bill of Materials (BOM) that lists all managed
container images by name, tag, and digest.

### Download the BOM

```sh
# CycloneDX JSON format
curl -fsSL \
  https://cd.splunkdev.com/sok/splunk-operator/-/releases/v{VERSION}/downloads/bom/bom-v{VERSION}.json \
  -o bom.json

# Human-readable text format
curl -fsSL \
  https://cd.splunkdev.com/sok/splunk-operator/-/releases/v{VERSION}/downloads/bom/bom-v{VERSION}.txt \
  -o bom.txt
```

### BOM Contents

The CycloneDX BOM (`bom-v{VERSION}.json`) lists:

- **Standard operator image** (`splunk/splunk-operator:{VERSION}`) — multi-arch
  manifest covering `linux/amd64` and `linux/arm64`
- **Distroless operator image** (`splunk/splunk-operator:{VERSION}-distroless`) —
  minimal base, `linux/amd64`

Each entry includes the image `purl`, manifest digest (SHA-256), and platform
metadata.

### Verify Image Digests Using the BOM

```sh
# Pull the manifest digest from the BOM
jq -r '.components[] | select(.name | contains("distroless") | not) | .hashes[0].content' bom.json

# Compare against the live registry
crane digest splunk/splunk-operator:{VERSION}
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI artifact fan-in | BOM files pass from generate-release-bom job to gitlab-release-record job via GitLab CI artifacts |
| gitlab-release-record -> GitLab Package Registry | Script uploads files via authenticated API call |
| docs as authoritative verification instructions | Committed markdown is the source of truth for user-facing verification commands |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-07 | Tampering | BOM artifact between CI jobs | accept | GitLab CI artifact mechanism provides integrity within a pipeline run; artifact checksum verified by GitLab runner |
| T-03-08 | Tampering | docs/supply-chain-verification.md | accept | File is committed to git; any modification is git-traceable; protected branch rules on main prevent unauthorized commits |
| T-03-09 | Repudiation | Which BOM was attached to which release | mitigate | BOM JSON metadata.timestamp recorded; signing-summary.md includes manifest digests; GitLab release API records asset upload time and CI pipeline ID |
| T-03-10 | Information Disclosure | Release page URLs in docs | accept | URLs reference cd.splunkdev.com (internal GitLab) — publicly accessible only to authenticated Splunk employees; no secrets disclosed |
| T-03-11 | Spoofing | cosign.pub authenticity in docs | mitigate | Docs reference cosign.pub from git repository URL (raw.githubusercontent.com/splunk/splunk-operator/main/cosign.pub); HTTPS + GitHub's CA chain authenticates the source; public key is committed to the protected main branch |
| T-03-12 | Elevation of Privilege | allow_failure bypasses failed BOM generation | accept | allow_failure intentional per PIPE-04 for graceful rollout; same disposition as generate-release-sbom; to be removed after BOM job is proven stable |
</threat_model>
